## D3 — M1 omits directory reparse points instead of detecting cycles

- **Date:** 2026-09-15
- **Status:** approved (requested by the human in the M1 fix round; the finding itself came from the mandatory OCR review)
- **Context:** M1's traversal called `Directory.GetDirectories(path)`, which returns junctions/symlinks as ordinary directories and then recursed into them. `UI_SPEC.md` §6 requires iterative traversal and ties cycle detection to `followSymlinks`; a junction pointing back at an ancestor therefore made M1 loop forever (OCR high finding against `MarkdownListing.cs`). M1 implements neither the `(link → target)` line (M2) nor `FollowSymlinks`/cycle detection (M3).
- **Decision:** M1 enumerates directories with `EnumerationOptions { AttributesToSkip = FileAttributes.ReparsePoint }`, so reparse points are omitted from the listing entirely. M2 relaxes this to "enumerate reparse points, emit `(link → target)`, do not recurse", and M3 adds the followed/cycle-detected case. Recorded as **L2** in `KNOWN_LIMITATIONS.md` and as **LEARN[3]** in the code.
- **Alternatives considered:** (a) leave the behaviour and only document it — rejected: an unbounded loop/OOM is an unacceptable failure mode for a released-looking skeleton; (b) implement `(VolumeSerialNumber, FileIndex)` cycle detection now — rejected as scope creep into M3; (c) emit the §5 link line now — rejected as scope creep into M2, whose named test `LinkNotFollowed_EmitsLinkLine` owns that format decision.
- **Consequences:** M1's output omits junctions/symlinks (a visible, documented gap) instead of hanging. `MarkdownListing.cs` gains one static `EnumerationOptions` field plus LEARN[3]. M2 must revisit the guard; the limitation row stays `open` until then. Explicitly **not** a deviation from `PLAN.md`'s M1 scope — it is a safety guard inside it.
- **Approved by:** human, dsh session, "REQUEST CHANGES M1: (1) Add minimal reparse-point guard in MarkdownListing.cs …"

## D5 — A root-folder failure propagates; only nested directories get `(access denied)`

- **Date:** 2026-09-15
- **Status:** approved (requested by the human in the M2 fix round)
- **Context:** M2's first implementation ran the root through the same recovery as any nested directory, so a missing or unreadable root produced `- [{RootName}] (access denied)` and `Generate` returned normally. `UI_SPEC.md` §5's table defines `(access denied)` only for a *folder inside* the listing — the root row has no such variant — and §7's CLI contract has exit codes that must distinguish "could not list anything" (1/2) from "listed a tree that contained an unreadable subfolder" (0).
- **Decision:** the root's children are read through `ReadRootChildren`, which has no catch: `UnauthorizedAccessException`/`IOException` from the root reach the caller. Only nested directories go through `ReadChildren`, which converts a failure into the `(access denied)` line and continues with siblings. Test: `NonexistentRoot_Throws`.
- **Alternatives considered:** (a) keep the M2 behaviour and document it — rejected: it hides a total failure behind a listing that looks like a partial success, and it breaks the CLI's ability to report exit 1/2; (b) emit a different root-specific line — rejected: no §5 grammar for it, and inventing format is forbidden; (c) both throw and emit — rejected as contradictory.
- **Consequences:** `Generate`'s XML documentation now declares `IOException`/`UnauthorizedAccessException`; the M1 `MainWindow` `MessageBox` path is reachable again. M6's CLI must map these to exit codes 1 (folder not found) and 2 (enumeration failed).
- **Approved by:** human, dsh session, "REQUEST CHANGES M2: (1) Root failure must propagate to the caller …"

## D6 — A reparse point without a target is omitted, not given an invented line

- **Date:** 2026-09-15

After classifying by `FileAttributes.ReparsePoint`, those entries have no target to print, and `UI_SPEC.md` §5 has no line for "reparse point with no target".

## D9 — The folder-size walk is iterative and never enters reparse points

- **Date:** 2026-09-15
- **Status:** approved (requested by the human in the M3 review round; item 2)
- **Context:** the first M3 implementation summed folder sizes with a mutually recursive `SumEntries`/`SumFolder` pair, which (a) violated the iterative-traversal requirement of UI_SPEC §6 and LEARN[2] — a 300+ level tree could overflow the call stack while summing — and (b) recursed into reparse points when `followSymlinks` was on, so a junction cycle made the walk unbounded until the entry budget stopped it. The corrected §5 rule 7 now states flatly that "reparse points are never entered for sums, in either link mode".
- **Decision:** `TryMeasureFolder` is an explicit-stack walk. It never enqueues a reparse point (directory or file) regardless of the link mode, respects rule 5's hidden filter for sums, observes the cancellation token on every iteration, and keeps the `Budget` cap (an exhausted budget marks the sum partial rather than hanging). The "first popped directory is the measured folder" convention distinguishes "the folder itself is unreadable → no size" from "a nested subtree is denied → partial sum".
- **Alternatives considered:** (a) keep recursion and add cycle detection — rejected: the stack-depth hazard would remain; (b) keep recursion but stop entering reparse points — rejected: fixes one of the two defects; (c) memoise subtree sums — rejected: does not remove the need for an iterative walk and has no measured need.
- **Consequences:** UI_SPEC §6's "never recursive" guarantee now covers the size path as well as the listing path. A folder whose content is reachable only through a junction reports less than the target physically holds — kept as limitation **L5**. New tests: `ShowFolderSizes_FollowSymlinks_CyclicJunction_Terminates` (bounded wait) and the reworked `Rule7_*`/`FollowLink_*` expectations that no longer count link-target bytes twice.
- **Approved by:** human, dsh session, "REQUEST CHANGES M3: (2) Rewrite the folder-size walk as iterative … never enter reparse points in either mode …"

## D10 — Cycle detection is ancestry-based

- **Date:** 2026-09-15
- **Status:** approved (requested by the human in the M3 review round; item 4)
- **Context:** the first M3 implementation kept a set of every directory it had ever expanded and treated a link whose target was in that set as a cycle. That reports a false cycle for a link to a directory that merely appears elsewhere in the tree — e.g. a sibling listed earlier — silently downgrading it to the not-followed form even though following it terminates. UI_SPEC §6 says a link's target children are listed as normal entries, so a target reachable twice must be listed twice.
- **Decision:** a cycle is a link whose target identity is on the **current expansion path** (one of the frame's ancestors). The traversal keeps the ancestor identities in a level-indexed list that is truncated to the frame's level before each directory expansion or link check, so a sibling's identity is dropped before the check and a sibling link is followed. Identity reads happen only when `followSymlinks` is on (M3 review item 3), since a link is never entered otherwise.
- **Alternatives considered:** (a) the "every expanded directory" set — rejected: false cycles, as above; (b) a per-link visited set cleared afterwards — rejected: extra bookkeeping that still has to distinguish ancestors from siblings; (c) resolved-path comparison — rejected in LEARN[6].
- **Consequences:** `visited` becomes `pathIdentities` (`List<FileIdentity>`), with `TruncateTo` maintaining the invariant; LEARN[9] documents it. `FollowLink_ToAlreadyListedSibling_IsFollowed` pins the sibling case, and `FollowLink_CycleTerminates` / `NotFollowed_CycleTerminates` still pass. The default (`followSymlinks = false`) now performs no identity reads at all.
- **Approved by:** human, dsh session, "REQUEST CHANGES M3: (4) Cycle detection is ancestry-based (D10) …"

## D12 — A depth-limited followed link renders the bare link form

- **Date:** 2026-09-15
- **Status:** approved (raised as a question in the M3 round-2 report; ruled on in the M3 round-3 request)
- **Context:** UI_SPEC §5 rule 4 says a folder at `level == depth` still gets its line but neither its files nor its subfolders. Rule 11 says that with `followSymlinks` on the suffix becomes `(link → target → followed)` *and the target's children are listed as normal entries*. For a link sitting exactly at the depth limit those two rules collide: the children cannot be listed, so the `→ followed` marker would promise content that rule 4 suppresses. The round-2 implementation chose the bare form and flagged it as an open interpretation.
- **Decision:** a link at `level == Depth` emits the **bare** link form `- [{relative/path}] (link → {target})` and is not expanded; the identity read is skipped as well, since nothing will be entered. The bare form is the truthful one: it reports what the engine actually did.
- **Alternatives considered:** (a) emit `(link → target → followed)` with no children — rejected: it claims a follow that rule 4 forbids, and a cyclic link at the boundary would additionally claim a follow that cycle detection would have refused; (b) expand anyway — rejected: contradicts rule 4 and reintroduces the depth bypass the round-2 fix removed.
- **Consequences:** `FollowLink_RespectsDepthLimit` pins the behaviour, asserting the bare line for the link and the plain line for its sibling folder at the same boundary. `NotFollowed_CycleTerminates` / `FollowLink_CycleTerminates` are unaffected (unlimited depth).
- **Approved by:** human, dsh session, "REQUEST CHANGES M3: … D12 (depth-limited followed link renders the bare link form)".

## D13 — The ancestry list keeps position == level, with a null slot for an unreadable identity

- **Date:** 2026-09-15
- **Status:** approved (requested by the human in the M3 round-3 request, from the round-2 OCR finding on `MarkdownListing.cs:695`)
- **Context:** D10 keeps the ancestor identities in a level-indexed list and relies on `TruncateTo(level)` removing every entry at index ≥ that level. The first implementation appended **only readable** identities, so a directory whose identity read failed left no slot and every deeper entry landed one or more positions below its true level. Consequence: when the traversal returned to a shallower frame, `TruncateTo` removed fewer entries than it should, so a *previous branch's* descendant could survive in the ancestry list — and a link targeting it was then misreported as a cycle and printed in the not-followed form, even though it is not an ancestor (a D10 violation and a wrong listing).
- **Decision:** `pathIdentities` is a `List<FileIdentity?>` and **one slot is appended per expanded directory unconditionally** — the directory's identity, or `null` when the read fails. Position therefore always equals tree level, so truncation is exact and no stale entry can survive. A `null` slot never equals a real identity, so an unreadable ancestor cannot be recognised by identity at the first encounter; the link is followed once, which records the target's identity, and the next encounter is detected as a cycle — termination is preserved (see `CycleWithUnreadableAncestorIdentity_Terminates`).
- **Alternatives considered:** (a) store `(identity, level)` pairs and compare by recorded level — equivalent in effect, but it needs a comparison loop on every check and a level field that the list position already encodes; (b) skip the append on failure (the buggy behaviour) — rejected, as above; (c) resolve and compare ancestor *paths* as a fallback for unreadable identities — not adopted: LEARN[6] records why path comparison is unreliable (8.3 names, `\\?\` prefixes, mapped drives), and the chosen fix restores the invariant without a second identity mechanism.
- **Consequences:** `TruncateTo` and `Remember` document the invariant; `Remember` is a one-liner that always appends. Two tests were added: `FailedIdentityRead_KeepsAncestrySlotsAligned` — verified to **fail** against the pre-fix behaviour (the link came out bare, i.e. misreported as a cycle) and to pass with the fix — and `CycleWithUnreadableAncestorIdentity_Terminates`, which pins termination and the one-extra-level behaviour the review asked for.
- **Approved by:** human, dsh session, "REQUEST CHANGES M3: One item. Fix the ancestry-list index/level invariant in the cycle detection … Record as DECISIONS.md D13 …".

## D15 — `SettingsStore.SaveTo` writes atomically (temp file, then move)

- **Date:** 2026-09-15
- **Status:** approved (requested by the human in the M4 round-2 request, from the round-1 OCR finding on `SettingsStore.cs:99`)
- **Context:** the first M4 `SaveTo` truncated and rewrote `settings.json` with a single `File.WriteAllText`. A crash or power loss mid-write leaves a truncated file, and because §4 maps *any* unreadable content to defaults, that failure mode silently loses all eight persisted settings — the app starts clean and the user never learns why.
- **Decision:** serialise to a uniquely named temp file **in the same directory** (`settings.json.<guid>.tmp`), then `File.Move(temp, path, overwrite: true)`. A failure after the temp write deletes the temp file in a `catch` and rethrows the original error, so no residue and no swallowed failure. Tests: `Save_LeavesNoTempFileBehind` (the directory holds exactly the settings file) and `SaveTwice_ReplacesFileAndKeepsOnlyTheLatest` (the overwrite path plus the newest values).
- **Alternatives considered:** (a) keep the in-place write — rejected: silent total loss of settings; (b) write the temp file under `%TEMP%` and move it — rejected: `File.Move` is only atomic within one volume, and `%TEMP%` is often on a different drive; (c) `File.Replace` — rejected: it requires the destination to exist, so a first-ever save would still need a separate path.

## D21 — One owner rule for the §3.5 status line

- **Date:** 2026-09-15
- **Status:** approved (requested by the human in the M5 round-4 request, closing OCR run-3 findings 1–3)
- **Context:** after the round-2 and round-3 fixes the status line still had no single owner: surfacing a settings-save failure was a **per-call-site obligation** (`ShowSaveError()` after `PersistSettings()`), which is exactly how the browse path missed it in round 2; `SaveButton_Click` reported its own failure through a different mechanism (`SetStatus(Error, …)` without a pending field), so a later progress/ready update could erase a Save-as failure (run-3 finding 1); the copy-feedback timer was not owner-aware and could paint `Ready` over a running enumeration (finding 2); and the recovery repaint tracked "the settings save failed" rather than "the line is showing that failure" (finding 3).
- **Decision:** the window keeps **one** pending write failure — `(SaveKind Kind, string Message)?` — written by *both* writers (the settings file and a Save-as export) and cleared only by a later success **of the same kind**, which then repaints. Every path that used to paint `Ready` unconditionally now paints the owner state (`RepaintOwnerState`): the pending failure if there is one, otherwise `Ready`. Throttled progress may show during a run, but the run's end repaints the owner state, so a failure always wins the final state. The copy timer borrows the line: it records that its own text is showing, and when its window closes it acts **only** if that text is still there and no run is in flight — otherwise it does nothing. Enumeration and clipboard failures stay transient, because no later action of the same kind could clear them.
- **Alternatives considered:** (a) keep the per-call-site `ShowSaveError()` discipline — rejected by evidence: one call site out of five missed it, and the same class of miss produced the round-2 finding; (b) a small status-owner class with subscribers — rejected as more machinery than a single line and a single pending message need (karpathy-guidelines §2); (c) suppress progress entirely while a failure is pending — rejected by the round-4 instruction ("throttled progress may show during a run, but the end state is the pending failure"); (d) treat enumeration failures as owned too — rejected: they are transient by nature (there is no "same kind of action" that would clear them), and remembering them would mean a stale error could never be cleared.
- **Consequences:** the status line now has one rule a reviewer can check in one place, and the round-3 findings are structurally closed rather than patched at a call site. Two implementation details are part of the rule and carry comments in the code: `SetStatus` records whether the copy feedback currently owns the text, and each progress report carries the run it belongs to — without that, a report still queued on the dispatcher when a run finished could repaint `Enumerating…` over the state the completion had just restored, which the round-4 machine check actually caught ("2 s after the failing toggle: `Enumerating… 1 entries`" where the failure was expected). Machine-verified after the fix: a settings failure survives a toggle-triggered regeneration; a pending failure is restored after the copy feedback window; a copy during a run leaves the line on `Enumerating…`, not `Ready`; a same-kind success clears and repaints. `SaveButton_Click`'s catch routes through the same field, verified by code audit rather than by driving the modal Save-as dialog (L8(c)).
- **Approved by:** human, dsh session, "REQUEST CHANGES M5: one final round. (1) Implement a single status-owner rule in MainWindow.xaml.cs … Record as D21 in DECISIONS.md."

## D21 (revision) — the owner painter yields to a run in flight, and the failure mapping collapses into it

- **Date:** 2026-09-16 (M6)
- **Status:** implemented in M6 — requested by the human in the `APPROVE M5` message as "a small declared hardening task within M6", from the two watch items carried out of OCR run 4
- **Context:** D21's owner rule left two low-severity refinements, both found by OCR run 4 and reported in the M5 report: (1) `RepaintOwnerState` painted unconditionally, so a successful Save-as repaint (`MainWindow.xaml.cs:156` then) or `PersistSettings`' recovery repaint (`:446`) could replace a running enumeration's `Enumerating… {n} entries` with `Ready` while the run continued; (2) `ShowPendingFailure` and `RepaintOwnerState` each held a copy of the pending-failure → `Error` mapping (`:463`), i.e. the "one place" the rule claims was not quite one place.
- **Decision:** two changes, both inside D21's rule rather than beside it.
  1. `RepaintOwnerState` returns immediately while `_enumeration is not null`. The yield defers the paint, it does not drop it: the run now retires itself (`_enumeration = null`) in its `finally` **before** calling the painter, so the completion repaint is not suppressed by the very run it finishes, and any throttled progress report still queued for that run is dropped at the same moment. The transient enumeration failure keeps the line, because the `finally` skips the repaint when the run ended in that failure (otherwise the transient error would be replaced by `Ready`).
  2. `ShowPendingFailure` is deleted; its five call sites (`BrowseButton_Click`, `CommitDepth`, `FolderSizesToggle_Changed`, `IndentRadio_Checked`, `ApplyToggle`) call `RepaintOwnerState`.
- **Alternatives considered:** (a) let each caller check `_enumeration` itself — rejected: that is the per-call-site obligation D21 removed, and the two sites above are the evidence that such obligations get missed; (b) keep `ShowPendingFailure` and give it the yield too — rejected: two methods with the same condition is two places to keep in step; (c) skip the repaint entirely when a run is in flight — rejected: a pending failure could then vanish for good; (d) move the completion repaint after `_enumeration = null` while leaving the old pre-clear repaint in place — rejected: one of the two would be dead code.
- **Consequences:** one condition in one method decides who may paint; a repaint requested during a run is visible when that run ends. Two deliberate behaviour changes fall out of collapsing the call sites, and are reported rather than hidden: (i) a settings change made while no folder is selected now repaints `Ready`/the pending failure where it previously left whatever was on the line, so the D16 startup `Notice` is cleared by the first settings change (D20's `Notice` is not an owner state); (ii) the §3.5 copy feedback can be replaced by the same repaint inside its 2.5 s window if the user changes a setting in that window (`SetStatus` clears `_copyFeedbackShowing`, so the timer then does nothing). Both are consistent with D21's "a later action takes the line back", and both are listed in the M6 report.
- **Second revision (M6 fix round — items 4 and 5 of `REQUEST CHANGES M6`), which closes OCR run-6 findings 3 and 6:**
  1. **The completing run's skip is narrowed.** `GenerateAsync`'s `finally` now guards with `!enumerationFailed || _pendingFailure is not null`: the transient enumeration message keeps the line only while nothing else owns it, so a write failure recorded *during* the run (a failed Save-as — its button stays enabled while running) still wins. Without this the failure stayed set but invisible, contradicting D21's own rule.
  2. **The five collapsed call sites are guarded with `_pendingFailure is not null`.** With no run in flight, `RepaintOwnerState` would otherwise paint the idle `Ready` state over the D16 startup notice or over live copy feedback — consequence (i) above, now removed. The pending-failure mapping still exists once; what each site decides is only whether *that* action has anything to say.
  Machine-checked afterwards: with the settings file unwritable and the listed folder made unreadable, the toggle leaves the line on `Settings could not be saved: …` and **not** on the bare `Access to the path … is denied.`; and booting with a stale `lastFolder` shows the notice, which a settings change no longer erases.
- **Approved by:** human, dsh session, `APPROVE M5 — recorded with two M6 watch items … (1) RepaintOwnerState must yield to a run in flight … (2) collapse ShowPendingFailure into RepaintOwnerState … to be fixed as a small declared hardening task within M6.` The second revision was requested by the same human in `REQUEST CHANGES M6`, items 4 and 5.

## D23 — The §7 command line: how CLI mode is selected, and which failure is which exit code

- **Date:** 2026-09-16 (M6)
- **Status:** declared in M6; the parts that interpret `UI_SPEC.md` §7's silence are listed explicitly so the gate can overrule them
- **Context:** §7 fixes the synopsis, the delivery behaviours ("default → clipboard + toast", "`--to` → file"), and three exit codes (0 ok, 1 folder not found, 2 enumeration failed), but is silent on: how a malformed invocation is classified, what a valueless `--folder` means, whether a write or clipboard failure gets its own code, whether the toast also appears on the `--to` path, and how unknown arguments are treated (M7's notification activation passes one).
- **Decision:**
  - CLI mode is selected by the presence of `--folder` **or** `--to`, so a `--to`-only invocation gets the §7 failure instead of a window appearing.
  - Missing or valueless `--folder` → one usage line on stderr, exit **1** (the folder was not given, so it cannot be "found"; §7's set of codes stays closed at 0/1/2).
  - The `--to` path writes through `ListingFile.Save` (§5 rule 12, UTF-8 without BOM) and shows **no** toast — §7 names the toast for the clipboard default only.
  - A write failure or a clipboard failure → stderr + exit **2** (there is no fourth code; `PLAN.md`'s M6 task text already maps a clipboard failure to exit 2).
  - Failures also toast when `Environment.UserInteractive` is true — §7's "when interactive". A toast that fails to show prints a warning on stderr and does **not** change the exit code: the code describes the listing, not the notification.
  - Unknown arguments are ignored, so the notification platform's activation argument cannot turn a working command into a failure.
- **Alternatives considered:** (a) treat `--to`-only as "not CLI mode" and open the window — rejected: a caller that passed `--to` plainly intended the CLI, and a window is the one thing §7 forbids; (b) a distinct usage exit code — rejected: a spec-defined set stays closed; (c) toast on the `--to` path — rejected: not in §7, and the Explorer verb (M7) uses the clipboard path anyway; (d) `--folder=<path>` as an additional accepted form — rejected (LEARN[28]); (e) reference only the M6 code's own catch for enumeration failures — rejected: the CLI needs a `Directory.Exists` pre-check to distinguish §7's exit 1 from exit 2 at all, and the engine's own root failure then stays unreachable through the CLI (see L10).
- **Consequences:** the CLI's behaviour is fully specified for the gate. One gap is recorded rather than papered over: because the engine's enumeration silently ignores an unreadable directory (`EnumerationOptions.IgnoreInaccessible` defaults to `true` and the engine never turns it off), an existing-but-unreadable root is not an "enumeration failed" case today — the CLI reports exit 0 with a one-line listing. That is **L10**, reported with its evidence; **resolved in the M6 fix round** (item 1 of `REQUEST CHANGES M6`): the option is now `false`, a denied child folder produces the §5 `(access denied)` line and the `~` partial sum, and a denied root exits **2** through the engine's own throw (machine-checked; L10 is marked resolved).
- **Extension (M6 fix round, item 2 of `REQUEST CHANGES M6`):** a valueless or blank `--to` is a **usage failure — stderr + exit 1**, not a fallback to the clipboard. The rule's sibling was found by OCR run 6: `--folder X --to` used to leave the output path unset, so the run copied to the clipboard, toasted "markdown copied to clipboard" and exited 0 for a caller who had asked for a file. The parser now represents "given without a value" as an error, so the clipboard sink is only ever used when `--to` was absent entirely. Every usage failure prints one line — `FolderTreeMD: <reason>. Usage: <synopsis>` — and the reason names the option at fault (`--folder is required`, `--folder needs a folder path`, `--to needs a file path`).
- **Second extension (M6 fix round 2, item 1 of the second `REQUEST CHANGES M6`):** a known option written in the single-token `--name=value` form is a **usage failure — stderr + exit 1**. It is neither *accepted* (this entry's alternative (d) rejected widening the contract; §7 writes the space-separated form) nor *ignored* as an unknown argument, which is what the parser did and what OCR run 2 finding 3 caught: `--folder C:\data --to=C:\out.md` dropped the output path and copied to the clipboard with exit 0, and `--folder=C:\data` alone fell through to the window request. Pinned by table rows in `CliCommandTests`.
- **Approved by:** _pending — listed here for the M6 gate, per the same rule as D22 (the extension was requested by the human in `REQUEST CHANGES M6`)._

## D24 — The §7 argument scan is a pure parser in Core

- **Date:** 2026-09-16 (M6 fix round)
- **Status:** implemented in the M6 fix round, requested by the human in `REQUEST CHANGES M6` item 2 ("Move the argument scan from `App.xaml.cs` into Core as a pure parser (D18 precedent; record as D24) with table-driven tests")
- **Context:** M6's first version kept the scan as a `private static` method on the WPF `App`, so the one piece of M6 logic with real boundary conditions had no automated coverage: the test project targets `net8.0` and references Core only (LEARN[1], D4), and `InternalsVisibleTo` cannot bridge an incompatible target framework. OCR run 6 then found two genuine defects in exactly that method (an option consuming the next option as its value; a valueless `--to` silently downgrading the delivery).
- **Decision:** `src/FolderTreeMD.Core/CliCommand.cs` holds the §7 grammar as a **pure** value-producing parser: `CliCommand.Parse(string[])` returns a command whose `Kind` is `NotACliRequest`, `ListFolder` or `UsageError`, with the folder, the optional output path, or the usage message. `App.xaml.cs` only decides what to do with the result (exit before any window), and `CliRunner` only executes a command. Value semantics: either option in any order; unknown arguments ignored; a repeated option keeps its last value; **an option token is never consumed as a value** (`--folder --to out.md` is a usage failure); a missing, blank or whitespace-only value is a usage failure naming that option; a `--to` without `--folder` is a usage failure; CLI mode is selected by either option's presence. The §7 synopsis is a constant in the same type, so every usage message carries it.
- **Alternatives considered:** (a) leave the scan on `App` and rely on manual CLI runs — rejected: that is what produced the defects, and the milestone's DoD asks for machine-repeatable evidence; (b) add a `net8.0-windows` test project for one pure function — rejected: a structural change to `PLAN.md`'s layout (the reasoning recorded in D18/D19), and unnecessary once the parser is in Core; (c) make the scan `internal` on `App` and expose it with `InternalsVisibleTo` — impossible: the test project cannot reference a `net8.0-windows10.0.17763.0` project at all; (d) put the parser in the WPF project but test only the exit-code mapping end to end — rejected: the boundary cases (option-as-value, valueless options, repeats) are exactly what a table can pin in milliseconds.
- **Null tolerance (M6 fix round 3, item 1 of the third `REQUEST CHANGES M6`):** `Parse` takes `string?[]`, and a `null` element is an unknown argument to skip — exactly what the pre-`=` scan did. A `null` in a value position is "no usable value", so the option it follows fails the way an absent value does. The `=` rule introduced a `NullReferenceException` on this public API for one round; OCR run-3 finding 2 caught it, and `CliCommandTests` now pins all three shapes (`[null]`, `[null, "--folder", …]`, `["--folder", null]`, `["--to", null]`).
- **Consequences:** §7 grammar, plus three user-facing strings, joins Core's public surface — the same documented layering concession as D18, inert inside a pure function. `CliCommandTests` is a table of 28 argument lists plus 3 valueless-`--to` cases; the pre-fix defects are table rows. `LEARN[28]` (the scan's previous home) is superseded by `LEARN[30]`, and the file is a declared addition to M6's file list (D22).
- **Approved by:** _pending — the human requested the move in `REQUEST CHANGES M6` item 2; this entry records how it was done._
